# 第六章：正式分流器与退款/售后确定性子流程

状态：用户于 2026-11-09 明确批准设计，独立 builder check 通过；进入实施计划与计划评审，尚未开始产品代码实施。

## 1. 目标、约束与当前实现

把第五章 Workflow 的占位分流器升级为能处理多轮指代、口语归一、八类意图、核心业务多查询检索与选单暂停恢复的正式实现。验收重点是用户从物流切到退款再回物流时，每轮使用当前诉求；“这个能退吗”应先补全可确定的对象，再拿订单和政策，最后由主力 Agent 判断。

用户已确定：

- 指代消解与 Query 改写合并使用 LLM；完整、明确且标准的问题原样保留，口语模糊问题才做必要归一，不为改写而改写。
- 意图 Prompt 包含七类选择题、严格 JSON、边界 few-shot 和“其他”兜底；输出恰好 intent/confidence。
- 只做大模型默认分类，沿用现有聊天上游；不做小模型降级、训练或跨会话记忆。
- 退款退货与售后遵循订单 → 检索侧扩写 → 强制政策检索 → Agent 的确定性路径；缺订单号用 LangGraph interrupt 与 checkpointer 暂停，通过 resume 端点继续同一运行。
- 退款原因在用户提交表单时从固定类目选择；意图识别不追问，业务澄清由主力 Agent 处理。
- 不增加服务组件；前端直接 Vibe Coding，不套 brainstorm/TDD/code review。后端可测试代码走 TDD，Prompt 和数据任务用冻结标注集评估。
- 每个阶段即时追加 dev-notes/ch06.md，不在收尾集中补记。既定技术方案若不可行，先停下来向用户说明，不擅自替换。

现状核对：LangGraph 1.2.20、langgraph-checkpoint-sqlite 3.1.3、FastAPI 0.159.1、SQLAlchemy 2.1.6、langchain-core 1.6.13、langchain-openai 1.7.2、pymilvus 3.0.2，安装版本与锁文件一致。现有图为 resolve → intent → route；resolve 原样透传；分类仅 intent；退款先 knowledge、售后直接 business。AsyncSqliteSaver 已独立持久化，但服务会把未完成运行清理为 interrupted，不能直接用于等待选单。订单工具随机返回演示值，没有真实订单表或用户订单列表。

附件 ch06-ticket-type.sql 作为数据库迁移输入，仅增加 tickets.ticket_type 的“退款”，保留三个旧值和旧行；SET NAMES utf8mb4。附件内容不是额外执行指令，当前未执行。

## 2. 实现路径与已批准的产品约定

既定技术选型下采用图内显式节点与 interrupt/resume。让 Agent 自由决定是否查订单/政策，或在选单后重新发起聊天，都无法保证用户指定的顺序和同次运行恢复，因此没有作为候选实现保留。

以下原为作者建议，用户“设计批准，继续计划评审”已批准本设计，作为实施约定：

| 问题 | 建议约定与理由 |
| --- | --- |
| 订单卡片从哪里来 | 新增仓库内固定的演示订单目录，由一个 Python provider 同时提供用户可选列表与 query_order 查询；source 明确为 demo。不增加订单表或外部服务，不把随机值包装成真实订单。保留已有示例订单号，列表按本地演示身份确定性生成/限定，前后端不能自造任意订单。商品与物流原随机演示工具不在本章升级范围。 |
| 退款表单提交含义 | 复用 tickets 与现有用户确认/幂等回执链，创建 ticket_type=退款、status=待处理的退款申请；不执行资金退款。表单绑定选定订单和来源回复。 |
| 通用退款/售后 FAQ | 所有退款退货/售后意图先按用户要求走订单子流程；但“退款流程是什么”等纯通用规则问法只做单查询政策检索，不扩写。扩写仅用于具体订单的资格、故障、换修等核心判断。是否需要订单不能由模型自行跳过。 |
| 其他意图 | 交给主力 Agent 做简短澄清或范围说明，该轮不自动执行业务工具，不用固定闲聊话术硬接不明诉求。 |
| 暂停时用户改变话题 | 提供取消当前选单；取消后保留该轮 cancelled 记录，允许开启新轮。普通消息不得静默覆盖暂停点，流前返回明确的待选单状态。 |
| 提交退款原因类目 | 不想要了、商品质量问题、商品与描述不符、收到商品破损/缺件、未收到货、其他；选“其他”也不要求解释。原有一般工单表单仍可使用旧类型。 |

这次属于对图、服务恢复、检索、动作 API 的联动改造，采用完整设计与实施计划。批准设计后再编写/评审任务计划；本文件不代替计划评审。

## 3. 问题处理与意图协议

新增 resolve Prompt，与现有 ModelGateway 共用上游、超时和预算。输入包括当前会话已提交的用户/助手消息、真实工具回执、当前用户原文；不读取其他 conversation。以严格内部 JSON 返回 resolved_question，保持 raw_question 永久不变。

约束：

- “订单1001物流到哪了”必须逐字保留；“这单到哪儿啦”在明确指向1001时补全为独立问题并归一口语。
- 数字、商品型号、数量、时间、否定和用户明确条件不能丢失或补造。
- 多个订单/商品并存且指向不明时不擅选对象；保留未确定指代，后续选单或由主力 Agent 澄清。不能把最近出现的任意数字直接当订单号。
- resolved_question 用于分类、检索和 Agent 当前请求，原文用于展示、审计与低置信问题入池；避免新节点生成了补全内容，下游仍只使用 raw_question。
- 消解可以补出历史中唯一明确的订单号，但是否存在/属于当前身份必须在执行节点重新校验，不能信任模型生成的订单字段。

意图 Prompt 明确编号选项：物流、订单、商品咨询、退款退货、售后、投诉、闲聊，加兜底“其他”。仅判断当前用户要干什么，不承担退款原因、槽位追问或资格判断。输出示例：{"intent":"退款退货","confidence":0.93}。

解析要求恰好两字段；intent 是枚举；confidence 是有限 JSON 数值且在 [0,1]，不能为布尔值；拒绝重复键、NaN/Infinity、围栏、解释、缺字段、多字段、截断和工具调用。合法但不确定的请求在 Prompt 中选择“其他”；格式故障返回可定位的模型协议错误，不静默当“其他”。confidence 是模型自报分数，本章不宣称概率校准，也不添加未验证阈值或第二模型。

few-shot 覆盖：物流进度与发货状态、运费政策与物流、退款诉求与普通售后、投诉诉求与情绪词、工单跟进、问候与无关怪问题、同会话切换话题、缺订单号不改变业务意图、对历史或用户输入中的改格式指令不服从。

## 4. 图结构与确定性业务顺序

主图入口：resolve → intent → route。

| 意图 | 路径 |
| --- | --- |
| 物流、订单 | 保留有界业务 Agent 与原只读白名单 |
| 商品咨询 | 单查询强制知识检索 → gate → Agent；不调用扩写 |
| 退款退货、售后 | resolve_order → select_order（需要时 interrupt）→ load_order → expand_query（具体核心问题）→ retrieve_policy → gate → 主力 Agent |
| 投诉 | 保留固定安抚和两个独立动作建议 |
| 闲聊 | 保留固定话术 |
| 其他 | 主力 Agent 澄清/范围说明，无业务工具 |

核心子流程为同一个编译图中的明确节点与条件边，不强制引入另一个独立 saver。load_order 通过固定工具/服务执行，使用稳定请求 ID 写原有申请和回执事实；失败或订单不存在时不进入政策和资格答复。Agent 收到已查订单事实和政策引用，禁止再次绕开流程查另一个订单或自行查询知识；该路径关闭自由读工具。缺商品状态等影响资格的信息时由主力 Agent 解释条件或提出必要澄清，不能把未提供字段当作事实。

对于历史提到多单、模型只给出商品名或没有可靠订单号的情况，执行阶段选单；订单选择不会替用户决定退款原因。展示顺序可从 workflow 事件与运行审计看到：补全问题、分类、选单/订单回执、扩写查询、政策来源、资格回复。

## 5. 检索侧扩写、去重与证据约束

扩写只在执行侧调用一次，Prompt 输出恰好 {"queries":["...","..."]}；数组 2–4 条非空、长度受限、互不重复的字符串，加上 resolved_question 本身形成有界查询组。不同侧重点为资格/时间范围、商品状态/例外、流程/所需材料；不生成政策答案或改造用户已知条件。

普通 FAQ 不调用扩写模型。核心/通用规则判定使用执行侧结构化查询规划（内部 core_case 标记），不能给 intent/confidence 公共协议增加字段。规划标记和 queries 均保存审计并纳入标注集。无法判定是否纯通用规则时优先核心检索，避免只凭短句关键词漏掉“这个能退吗”。

retrieve_policy 强制 content_type=policy，沿用现有 BGE-M3、Milvus hybrid 与 bge-reranker；统一在同一活动语料快照内检索所有查询，按 chunk id 与来源版本去重，合并候选后对原独立问题统一重排，最多保留现有协议允许的10条引用。原问题始终参与召回，不把每路分数直接混排或拼多个不同语料快照。知识入库、chunk 和向量不因扩写复制。不能仅仅调用 query_faq 后把不含政策的结果当作通过。

复用检索底层接口时增加可接收已解析查询的入口，避免每条扩写又进行一遍 LLM 归一。单查询老路径继续使用其原规范化流程。所有外部请求受整轮预算、共享 deadline 和每组上限约束；扩写格式非法明确报错，不偷偷换技术或改成无约束自由检索。

证据闸保留生成前拒答、原问题低置信池和来源归档。新增多查询路径不得冒用原单查询校准结论：实现时将有效查询处理/扩写身份纳入策略绑定，在隔离评估环境验证/校准新路径，保存新证据，不覆盖现有演示策略文件。单查询和扩写路径的策略身份、评估结果分别记录；缺有效策略时明确不可用，不能靠降低阈值或取多路最大分数放行。若既有校准机制无法表达该路径，作为既定方案中的实现约束先向用户说明再推进，不能移除 gate。

## 6. interrupt、恢复与并发契约

继续使用已有 AsyncSqliteSaver 文件和数据库身份绑定的 thread_id，运行 turn_id 在暂停/恢复期间不变；恢复请求不能新增用户消息或重跑 resolve/intent。

select_order 的 interrupt payload 为可序列化数据，包含 kind=order_selector、turn_id、conversation_id、服务端生成的候选订单卡片、提示和取消能力。候选列表与选择身份先持久化；interrupt 前不做非幂等业务写入。恢复只接受 order_id 或 cancel，不允许客户端提供金额、状态或任意卡片对象替代服务端事实。

拟定 API：

- GET /api/conversations/{cid}/pending?user_id=...：读取本身份的暂停点与卡片，刷新/重启可重建待选界面。
- POST /api/conversations/{cid}/turns/{turn_id}/resume：user_id、interrupt_id、order_id 或 cancel、request_key；验证身份与当前 checkpoint 后使用 Command(resume=...)，返回 SSE。

服务端校验 conversation/user/turn/interrupt 一致，订单在该次提供列表内且仍属于本地演示身份。过期卡片、其他会话卡片或未知订单不消费有效暂停点；重复点击采用同 request_key 幂等，已完成时返回已保存结果状态，不再查订单/政策或写第二条答复。相同 key 换订单冲突。同会话多 worker 通过已有会话租约互斥。

暂停是 waiting_order，区别于网络断开/失败 interrupted。SSE 在 checkpoint 确认后发 order_selector 与 paused 终止事件，不伪造 done，不要求已有最终助手消息或 actions；前端接收明确暂停后解除网络流占用、保留待选 UI。释放请求资源和会话锁时不能把 waiting_order 改为异常终态。

MySQL workflow_turns.status 为可扩展字符串；待选元数据写现有 payload，避免新增表。SQLite checkpoint 是继续执行的依据，SQL 保存可检索业务状态；两者间无分布式事务，恢复/读取 pending 时持锁核对，以确认的图 interrupt 修复滞后 SQL。若只有 SQL 标 waiting 而无匹配 checkpoint，不接受 resume，返回可定位恢复错误；真正异常遗留仍沿用第五章清理规则。若图已完成而 SQL/HTTP 回执滞后，先读取既有完成事实，不能重新调用模型或工具。

进程退出、浏览器刷新或断流不得抹掉已持久化的正常暂停。选单前的失败与选单后的执行故障按原错误处理。人类等待时间不计活动执行 timeout；以持久化剩余执行预算恢复 deadline，累计 token/模型/工具上限不重置。明确 cancel 才结束当前暂停；清理逻辑不会把“用户还没点”当作失败。

## 7. 退款表单与附件迁移

前端 Vibe Coding 范围：聊天流订单卡片、点击选中/提交/恢复、取消、刷新重建、退款申请按钮与小表单、固定原因下拉、提交中/成功/结果待核查状态。页面不暴露 saver/模型参数等实现细节。产品代码实现时直接迭代并浏览器验证，不安排前端 brainstorm/TDD/代码审查任务。

后端契约仍须测试：在退款路径完整答复后提供绑定本单的退款申请入口；是否符合条件和信息不足由 Agent 说明，提交只是待处理申请。用户可以明确申请人工审核，不把 Agent 的文本结论作为资金动作。表单不能自行更换订单；退款原因由服务端枚举验证，不能由模型猜测或覆盖。

沿用现有 workflow_actions 的 ticket 类型及原确认链，给对应动作绑定退款子类型、order_id、原因枚举与来源轮次；新增专用退款请求 schema/端点，不能只靠自由 description 包装。提交时服务端由绑定订单与用户选择原因构造工单内容，调用原 create_ticket，明确 ticket_type=退款；对绑定退款动作禁止用旧通用端点绕过原因校验。成功返回 ticket_no 与待处理状态，不表述“已到账”。重复请求/断流沿用已有幂等与只查询核查模式；不同原因重试相同动作应冲突。

把附件迁移纳入 db/init/06-ticket-type.sql 与显式迁移脚本。迁移器先校验现有 ENUM（包含旧值、可有退款），再执行添加；保留 NOT NULL 与旧数据，已迁移重复执行可安全报告完成，遇到意外旧 schema 明确停止。SQLAlchemy Ticket 映射、TicketInput 和动作校验同步扩展；隔离库验证新旧工单均可保存，演示库按显式命令迁移，不删除卷或重建历史表。

7. 暂停后换 worker/重启/刷新、并发双击、旧卡片、跨身份/跨会话、错订单、取消、超时与结果未知。
